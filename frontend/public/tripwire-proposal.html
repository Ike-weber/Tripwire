Tripwire

The circuit breaker your wallet never had.

The brief — Smart Contract Financial Guardian Blockchain transactions are irreversible, while users and organizations may not detect malicious or abnormal activity until after funds have moved. Build a security layer that continuously monitors transactions and wallet behavior, detects abnormal activity, calculates risk, and interacts with smart contracts to provide configurable protection — transaction limits, delayed execution, or emergency controls.
Build window20 hours
ChainEVM testnet (Sepolia / XDC Apothem)
Base primitiveSafe{Wallet} + Zodiac Guard
Date2026-09-04

01 · Thesis

Protect the wallet, not the protocol.

Every serious entry in this space is protocol-side — infrastructure a dApp or rollup opts into. Tripwire is wallet-side: a self-custody guardian that protects a wallet or DAO treasury against anything it interacts with, with zero cooperation required from the other end.

The brief's own diagram is the spec. We build it literally, and each arrow is a real component, not a slide:

Brief's pipelineWhat we actually ship
BlockchainA Safe multisig (or single-owner Safe) on an EVM testnet, holding real testnet funds.
Real-time monitoringAn off-chain watcher that reads every pending Safe transaction the moment a signer proposes it — before it has enough signatures to execute.
AI risk analysisA rule engine + fork simulation + an LLM reasoning pass that turns raw calldata into a 0–100 score and a plain-English reason.
Suspicious transactionA drainer contract we write ourselves, that requests setApprovalForAll then calls transferFrom — the exact pattern behind most 2024–2026 wallet-drain losses.
Smart-contract protectionA Zodiac Guard on the Safe that reads the verdict and enforces limits, delay, or a full freeze — before the transfer executes.

02 · Landscape

Where the real gap is

SolidityScan — the tool named in the prompt — is a static/AI source-code scanner: it audits a contract before deployment. It has no runtime monitoring or wallet protection, so it isn't really competing in this lane. The real comparables, and why none of them solve the individual wallet's problem:

ProductWhat it doesWhere it livesThe gap it leaves
SolidityScan 700+ detector static/AI vulnerability scan, audit reports Pre-deployment, CI No runtime monitoring, no wallet-side protection at all.
Forta Firewall Pre-execution AI simulation, <10ms risk score, block above threshold Protocol / rollup RPC layer The target contract has to integrate it. A victim's own wallet is unprotected unless the dApp they got tricked by opted in.
BlockSec Phalcon Compliance AML/CFT risk feed checked before finalizing a tx Protocol-side compliance hooks Framed for regulators and protocols, not for a user protecting their own funds.
Harpie shut down 2025 Wallet-side drain protection Consumer wallet Proved the demand, failed on unit economics — not a reason to avoid the pattern in a 20-hour build.

Our edge: Tripwire sits inside the wallet's own execution path (a Zodiac Guard on a Safe), so it protects against any counterparty — a phishing site, a fake airdrop, a compromised frontend — and gives the owner real levers, not just an allow/deny bit: a spending limit, a cooling-off delay, and a panic switch.

03 · Concept

Sense → Reason → Act

Three pillars, mapped one-to-one onto the brief's diagram and onto the demo we'll actually run.

01

Sense

Watch every proposed Safe transaction the instant a signer creates it — while it's still sitting unsigned, before it can execute.

02

Reason

Score it: rule engine + a forked-chain simulation of the actual balance/allowance change, refined by an LLM that explains its reasoning in plain English.

03

Act

Write the verdict on-chain. The Guard reads it at execution time and allows, delays, or trips the breaker — the owner set the rules in advance.

04 · Architecture

How a transaction actually moves

The key constraint that makes this buildable in 20 hours: a Safe transaction isn't instant. A signer proposes it off-chain, it sits pending until enough signatures collect, and only then does someone call execTransaction. That pending window is exactly where our off-chain risk engine gets to do its work and write a verdict on-chain — the Guard never needs to make a synchronous off-chain call mid-transaction.

05 · Protection mechanisms

Three levers, configured in advance

Transaction limits

Per-tx cap and a rolling 24h velocity cap, tracked in the Guard's own storage. A tx over the line doesn't fail silently — it routes into the delay queue instead.

Delayed execution

Anything above the limit, or to a first-seen counterparty, sits in a timelock. The window is the risk engine's chance to review and cancel before it fires.

Emergency freeze

A critical score, or the owner's own panic button, trips the breaker: every outgoing call from the Safe reverts until a guardian explicitly unfreezes it.

06 · AI risk engine

What actually gets scored

Deterministic signal extraction feeds a fast rule-based base score; a forked-chain simulation and an LLM reasoning pass then adjust it and produce the explanation a human reads.

SignalWhy it matters
setApprovalForAll
0xa22cb465		Grants a third party control over an entire NFT collection — the single most common drainer primitive.
approve(spender, amount)
0x095ea7b3		Flagged hard when amount is type(uint256).max — an unlimited, indefinite allowance.
permit(...)
0xd505accf		Off-chain signature granting an allowance with no on-chain tx from the victim — invisible to naive monitors.
First-seen counterpartyContract or EOA the wallet has never interacted with before, weighted against wallet age.
Unverified / freshly deployed contractNo source on the block explorer, or deployed within the last few hours.
Amount vs. historical percentileValue far above the wallet's own p95 spend is anomalous even with no other signal.
Blacklist matchAddress appears on a scam-address feed (GoPlus Security API / ScamSniffer list).
Fork simulation diffReplay the exact calldata on an Anvil fork: does the wallet's real balance or allowance state change in a way nothing in the tx description admits to?

Scoring pipeline

Proposed tx → feature extraction → rule-engine base score → Anvil fork simulation → LLM reasoning pass (structured JSON: score, label, explanation) → verdict written to RiskRegistry.

The LLM's job is specifically the part rules are bad at: judging context. An unlimited approval to a well-known, verified DEX router is routine; the same call to a contract deployed 40 minutes ago that has already drained three other wallets is not — and the difference is exactly the kind of reasoning worth spending a model call on, not a rule worth hand-writing.

13 · Risks

What breaks a live demo, and the fix

RiskMitigation
Zodiac Guard API unfamiliar, burns hoursStart from Zodiac's own reference Guard template; test against Anvil before ever touching testnet.
Verdict lands after execution (race condition)Fail closed: any tx with no recorded verdict yet defaults to delay, never to allow.
LLM call times out or errors on stageRule-engine score always ships independently; LLM explanation is additive, never blocking.
Public testnet RPC flakiness during the live demoLocal Anvil fork as the primary demo environment; a recorded backup run as insurance.
Scope creep past checkpoint 2Integrator has unilateral authority to cut anything below P0/P1 after hour 14 — no debate on stage-day.
Relayer key is the one component with real custodyScope the relayer key to submitVerdict() only — it can never call a Safe execution function or move funds. Hold it in an env var for the demo, note KMS/HSM custody as a named follow-up, not a live gap.

14 · Appendix

Skeletons to start from

Guard hook

function checkTransaction(
    address to, uint256 value, bytes calldata data,
    Enum.Operation operation, uint256 safeTxGas,
    uint256 baseGas, uint256 gasPrice, address gasToken,
    address payable refundReceiver, bytes calldata signatures,
    address msgSender
) external override {
    bytes32 txHash = keccak256(abi.encode(to, value, data, operation));
    Verdict memory v = riskRegistry.verdictOf(txHash);

    if (v.status == Status.UNSCORED)      revert("tripwire: awaiting risk score");
    if (v.status == Status.FROZEN)        revert("tripwire: guard is frozen");
    if (v.status == Status.HIGH_RISK)     revert("tripwire: blocked, see dashboard");
    if (v.status == Status.DELAYED && block.timestamp < v.releaseAt)
        revert("tripwire: in cooling-off window");

    _enforceVelocityLimit(value);
}

LLM verdict schema

{
  "txHash": "0x9f2c...",
  "score": 87,
  "label": "high_risk",
  "reasons": [
    "setApprovalForAll to a contract deployed 41 minutes ago",
    "target contract is unverified on the block explorer",
    "3 other wallets interacted with this contract in the last hour, all followed by a transferFrom drain"
  ],
  "recommended_action": "freeze"
}

RiskRegistry (interface)

interface IRiskRegistry {
    enum Status { UNSCORED, LOW_RISK, DELAYED, HIGH_RISK, FROZEN }
    struct Verdict { Status status; uint8 score; uint256 releaseAt; }

    function submitVerdict(bytes32 txHash, Verdict calldata v) external; // relayer-only
    function verdictOf(bytes32 txHash) external view returns (Verdict memory);
}
